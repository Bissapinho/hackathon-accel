# 07 — Acceptance tests

Four levels: (1) platform checks, automated with Vitest against a local test database seeded with `fixtures/kumo-mini/`; (2) agent loop checks with the mock LLM; (3) deployment checks on Aiven (X1–X3 in §1); (4) a live demo rehearsal with the real model on the real Kumo data, judged on outcomes. All checks are on the API; the front is tested by its own team.

## 0. The `kumo-mini` fixture

The real Kumo files can't be committed. `fixtures/kumo-mini/` is a **synthetic** sample with the same file names, columns and value shapes, generated by a seeded script (`fixtures/generate-kumo-mini.ts`, task T-02b) and committed with its generator. It must contain:

| File | Rows | Built-in facts the tests rely on |
|---|---|---|
| `CLIENTS_NETSUITE.csv` | 20 | `ID_interne` unique; 2 inactive; zones `IDF` / `LYON` |
| `ARTICLES_NETSUITE.csv` | 30 | `ID_interne` unique; `DLC` like `J+3`; `Date_de_cr_ation` in `DD/MM/YYYY HH:MM` |
| `COMMANDES_NETSUITE_2025.csv.gz` | ≈ 1 500 lines | 120 `SO-` documents with positive quantities and 60 `RMA-` documents with negative quantities; `Lieu_Production` empty before 2025-08-01; 1 line whose article is not in the articles file; 2 clients with no documents |
| `CUISINES_REFERENTIEL.csv` | 3 | Kitchens `Gennevilliers`, `Frepillon`, `Draveil` |
| `CAPACITE_CUISINES_JOUR_2025.csv` | 3 kitchens × 30 days × 2 shifts | On 2025-10-14 `Gennevilliers` has 10 units of spare capacity and `Frepillon` is over capacity |
| other tables | ≤ 50 each | Same columns as the real files |

The expected numbers below are those of the generator's seed; if the generator changes, the tests are updated with it.

## 1. Platform (automated)

### Datasets (stage 1)
- **D1** Uploading `COMMANDES_NETSUITE_2025.csv.gz` creates version 1 with the fixture's line count, `Quantite` typed `integer`, `Date` typed `date`, `Lieu_Production` with the expected null count, and no parse errors.
- **D2** `ARTICLES_NETSUITE.csv`: `Date_de_cr_ation` typed `timestamp` (French format), `Article_Actif` typed `boolean` (`True`/`False`), `DLC` stays `string`.
- **D3** A CSV with `"abc"` in an integer column: the cell is null and `parse_errors` contains `{row, column, value:"abc", expected:"integer"}`. APPEND with different columns is refused with `COLUMNS_MISMATCH`; APPEND with the same columns creates version 2 with old + new rows.
- **D4** The profile of `No_Transaction` reports the prefixes `SO-` and `RMA-` with their counts; `profile_columns` with `matchAgainst` of `ID_Interne_Client_Netsuite` against `CLIENTS_NETSUITE.ID_interne` returns a match rate of 100 %.
- **D5** After uploading all fixture files, the bank draft holds one minimal card (term + mapping + evidence) per column; simulated datasets have a `scope` constraint.

### Semantics (stage 2)
- **S1** `edit_semantics` with a relation to an unknown term → `SEM_BAD_REFERENCE`; a relation type `belongs_to` → `SEM_BAD_VOCABULARY`; a term definition containing `SELECT` → `SEM_PROCEDURAL_CONTENT`.
- **S2** An evidence record with a query stores the server-computed result; a write query (`DELETE …`) is refused with `SQL_REJECTED`.
- **S3** Publishing with an open `block` constraint with options and no resolution is refused (`SEM_OPEN_DECISION`); after `resolveConstraint` it publishes `v0` with `resolution.by` = the current user.
- **S4** `browse_semantics {query: "retour"}` ranks the `Retour` term first when it has alias `RMA`; `resolve_semantics {mentions: ["taux de retour"]}` returns its mapping(s), the resolved constraint and its evidence.
- **S5** A published version is immutable: editing after publish goes into a new draft; `v0` is unchanged.

### Workspace: pipelines, objects, logic (stages 3–4)
- **W1** Applying `fixtures/expected-workspace.json` as draft ops then validating returns no errors.
- **W2** Validation errors: a pipeline with a cycle → `PIPELINE_CYCLE`; a check `unique(no_transaction)` on the line table → `PIPELINE_CHECK_FAILED` with a count; primary key on a non-unique column → `PK_NOT_UNIQUE`; missing description → `MISSING_DESCRIPTION`; an action setting a derived property → `RULE_SETS_READONLY`; a criterion calling an unknown rule → `CRITERION_UNKNOWN_RULE`.
- **W3** `preview_pipeline` on `commandes` returns ≤ 50 rows, an output row count of 120 and a passing uniqueness check; on `retours`, 60.
- **W4** Publishing builds the pipeline tables, creates `ont.*` and `logic.*` views and indexes; `SELECT count(*) FROM ont.commande` = 120; `pipeline_builds` has one row per output; re-publishing with unchanged inputs builds nothing ("up to date").
- **W5** Publishing with a stale `expectedRevision` → `VERSION_CONFLICT`; the draft is unchanged. History lists the version with its message, user, `via` and semantic version.
- **W6** A link with two keys (`lieu_production`, `date_production` → `CuisineJour`) joins correctly: every production lot from August has one kitchen-day.
- **L1** `logic.client.taux_retour` equals returned ÷ delivered computed by hand in SQL for 3 clients; a client with no orders has `NULL`, not an error.
- **L2** The rule `CuisineJour.surcharge` is true for Frepillon on 2025-10-14 and false for Gennevilliers.

### Objects and SQL
- **O1** Query "CuisineJour where `surcharge`" returns the expected kitchen-days; sorting by a derived property works.
- **O2** `get_object` on a commande returns its `client` link (1 row) and derived properties; on a client, its commandes and retours.
- **O3** `run_sql` rejects `DELETE`, `UPDATE`, `DROP` and multi-statements with `SQL_REJECTED`; a 6-second query is cancelled with `SQL_TIMEOUT`; results are capped at 500 rows with `truncated: true`; `logic.*` is readable.

### Actions
- **A1** `ReaffecterProduction` dry-run moving a 6-unit Frepillon lot of 2025-10-14 to Gennevilliers → `valid`, nothing written. Apply → `applied`; `ont.lot_production` shows the new kitchen; `logic.cuisine_jour.charge` of both kitchen-days changed by 6; the action log has one entry with before/after.
- **A2** Moving a 15-unit lot to Gennevilliers on the same day → `rejected` with the criterion message (capacity exceeded), evaluated with `afterEdits`; nothing written.
- **A3** `DeclarerInvendus` creates an object linked to a client and an article; it appears in `ont` and on both linked objects' pages.
- **A4** Re-upload `COMMANDES_NETSUITE_2025.csv.gz` as SNAPSHOT and re-publish → the moved lot keeps its new kitchen (edits survive the pipeline rebuild); object counts unchanged.
- **A5** A viewer can't run actions (`FORBIDDEN`).

### Deployment (on Aiven, once)
- **X1** `GET /api/health` on the deployed server returns `db: ok`; the server connects with TLS as `mini_app`; `mini_reader` can't write.
- **X2** `pnpm seed:kumo` loads the real files; all profiles reach `done`; disk use stays under 80 %.
- **X3** Publishing the rehearsal workspace completes; a second publish started meanwhile gets `PUBLISH_IN_PROGRESS`; after a re-upload of the order lines and a publish, the older version table is dropped.

### Stretch
- **P1** The kitchen planning app document validates; the object sets its blocks use return the right rows (metric values match SQL, kitchen-days over capacity first).
- **AU1** Enabling the over-capacity alert fires nothing. A move that puts a kitchen-day over capacity fires once (one event, one notification); moving more into it doesn't fire again.

## 2. Agent loop (mock LLM, automated)

- **G1** A tool call whose input fails its zod schema (or arrives truncated) returns `BAD_ARGUMENTS` as an `is_error` tool result; the session continues.
- **G2** A tool not allowed in the current mode returns `UNKNOWN_TOOL_FOR_MODE` with the hint to change mode; `change_mode` to `build` without a semantic version returns `NO_SEMANTIC_VERSION`.
- **G3** `publish_semantics` and `publish_draft` pause the session (`awaiting_approval`); **Reject** returns `REJECTED_BY_USER` and the loop continues; **Allow** runs the call. Tool calls after the gated one in the same response run after the decision, and all results go back in one user turn.
- **G4** `ask_user` with `multiple: true` pauses with `awaiting_answer`; answering with several choices resumes with the answer as the tool result.
- **G5** `edit_semantics`, `edit_draft`, `preview_pipeline`, `test_logic`, `test_action` never create approvals; `run_action` always does.
- **G6** Three identical failing calls stop the loop with a note.
- **G7** Stored assistant content is replayed byte-for-byte on the next request (thinking blocks included); no item is ever updated or deleted; the request carries `context_management` once the estimate passes the threshold.
- **G8** Every tool call item has a non-empty `rationale.title`, exposed in `AgentItemView` and in the SSE events (the front shows it).
- **G9** Chat blocks in assistant text are parsed (including `definition` and `decision`); invalid JSON blocks fall back to text.
- **G10** A response with `stop_reason: 'refusal'` ends the step with a plain message and no tool runs.
- **G11** Every `explore` answer writes a trajectory with the semantic version and the `resolve` calls.

## 3. Live demo rehearsal (real model, real Kumo data on Aiven, judged on outcomes)

Run the script in `02-slice-and-demo.md` §4 three times **on the Aiven database** (reset between runs with `pnpm db:reset-workspace`, which keeps the loaded datasets), through the API and SSE stream (a small CLI client, `pnpm chat`, or the front if ready). **Pass** when all of these hold each time (names and wording may differ):

| # | Outcome |
|---|---|
| R1 | Before proposing anything, the agent profiled the data (document prefixes, sign of quantities, keys, join match rates) — visible step cards |
| R2 | It proposed seed questions as checkboxes from the user's goal; it did not ask the user to write questions or ask anything the data answers |
| R3 | The published semantic version has enriched definitions for at least: order, return, client/store, article, kitchen, production load, capacity, return rate; each with evidence; simulated data labelled |
| R4 | At least one real ambiguity was settled as a multiple-choice decision and is applied downstream (the return rate follows the chosen base) |
| R5 | It showed a plan and a proposal in plain language before each first publish |
| R6 | Published: 72 677 orders and 62 814 returns (one per document), 893 clients, 1 135 articles, 5 kitchens; every order linked to a client; production lots and kitchen-days linked |
| R7 | Every object type, property, link, logic item and action has a description; most point at a definition |
| R8 | A return rate exists per client and per article and matches a hand-written SQL check on 3 rows |
| R9 | The move action is refused when it would put the target kitchen-day over capacity and applied otherwise; the agent tested both cases before publishing |
| R10 | "Which 5 stores have the highest return rate?" gets the right answer (check with SQL), a table or chart, and names the definition used |
| R11 | Nothing was published, run or enabled without an approval card; the final summary includes a verification block; no claim without a tool result behind it |
| R12 | Total time from first message to a working move action ≤ 15 minutes |

Record the best run **on `kumo-mini`** as `fixtures/demo-session.jsonl` for the mock fallback (a recording on the real data would contain Kumo values and can't be committed).
